# 04 — M-OPT 下的融合设计理解与待补需求

> 日期：2026-09-05｜版本：v0.5｜用途：内部产品对齐，不是排期承诺。
>
> 本轮收敛：先定会影响长期使用的概念与架构；运营、配置和外部接入另行分工，不把全部会议需求变成 POC 产品待办。
>
> 🔴 本轮必须澄清或设计；🟡 后续产品工作、运营配置或外部依赖；🟢 当前概念已对齐（Done），不代表功能已上线。

## 一、先把同一套逻辑说清楚

**本机的助理体系最懂我，分身在外面替我接住协作，专家提供专业执行能力。角色分工这一项要补的是：怎样让它们在不暴露我的私有权限和上下文的前提下配合起来。**

M-OPT 讲的是谁服务谁、谁代表谁、谁对结果负责；词典还要回答程序跑在哪里、用户在哪里调用、信息怎样传递。这两层需要对应，但不能看到用词不同就判定有 Gap。

### 1.1 三个角色，可以用同一套技术，也可以运行在不同设备上

| 角色 | 产品上承担什么 | 本轮的技术理解 |
| --- | --- | --- |
| 个人助理 / 全局助理 | 服务本人，归拢个人工作上下文与记忆，帮助工作和判断 | 以主力设备为个人私有工作中心；内部可有助理 A、B、C，再由全局助理在授权范围内汇总 |
| 分身 | 在指定业务域代表本人接收请求、沟通、跟进和回传 | 独立于本机运行。本人关机或暂时不在线，它仍能用已获授权的信息响应；“云端形态”首先表达这种独立性 |
| 专家 / 数字员工 | 提供可复用的专业能力，在任务中执行 | 按需调用，可由不同技术实现；不因为参与执行就成为群成员 |

所以，**“分身是云端形态”本身没有 Gap**。部署在云端，并不等于完整复制本机权限，也不等于获得替本人独立作业务决定的权利。技术底座是否相同，与角色权限如何划分是两件事。原 G03 不再作为冲突项保留。

同样，本机有多个助理或运行会话，不必被解释成 M-OPT 出现了多个对外角色。本轮将“全局助理”理解为个人侧统一服务与记忆归拢的位置，底下可以有多个执行工具。归拢范围需要本人授权，并不是天然读到所有会话。

这是结合本次讨论作出的产品映射，不是声称白皮书明确规定了多个本机 Agent 的实现方式。M-OPT 关于专业推理、零外联的严格措辞仍保留在原文中；具体部署与调用方案需据此评审，不能反过来把它直接翻译成“只能运行一个进程”或“本人不能借助 AI 辅助评判”。[M，第 2—6 页；D，§一；U]

### 1.2 本人在任务里 @ 助理，不等于把助理开放给项目

这里保留用户提出的工作方式：

1. 专家在任务里完成一份交付物。
2. 我在这个任务里 @ 自己的全局助理。
3. 助理结合本次任务、我的个人上下文、偏好与验收标准，给我一份评价和修改建议。
4. 我决定接受、退回修改，或者挑选建议提交到任务里。正式确认仍由人完成。

**这次调用是在共享任务旁边进行的一次私有工作，不是把助理变成共享任务成员。**

对应的产品边界应是：

- 只有本人能看到、@ 和调用自己的助理；其他成员的入口和接口都不能触发它。
- 助理用于评判的个人资料、调用过程和建议，默认仅本人可见。
- 本人选定的反馈或成果，经过明确发布动作后才进入共享任务；不把私有执行记录整段公开。
- 助理不成为正式任务负责人，也不因打开任务页就接受其他成员的派活。

词典已经写了“只有本人能 @ 自己的助理”，这个方向应保留。需要补的是**私有调用与共享回复之间的可见性和发布规则**，而不是删掉这个入口。[D，§一“助理”、§二“任务”]

责任与调用权限要分别控制：在当前设计里，不能让共享任务的分派路径变成别人调用本机助理的入口；也不能只隐藏 @ 菜单，却在后台继续允许调用。

### 1.3 专家不入群，这项已经收敛

数字员工进入融合产品后，可以作为专家能力参与任务；不再要求它拥有群成员身份。这与 M-OPT 和现有词典相容。

陈博希望“我不是一个人在干活，而是带着自己的团队工作”的体验仍然保留。它可以由个人工作台展示能力、任务、进度和成果来承载，不必把每个内部助理和专家都拉进组织 IM。[T，22:55—26:17；M，第 5 页；U]

## 二、🔴 先把概念和角色分工定清楚

**第一章已经能对应 M-OPT 的基本理念，不需要重新发明一套角色。现在要定的是会影响产品行为的边界。**

对照词典与现有 M-OPT 解读，还有三处需要说清：[D；01 解读，§三]

| 要定什么 | 为什么现在要定 |
| --- | --- |
| **谁负责，谁执行，谁确认正式结果** | 词典允许专家当“负责人”，但 M-OPT 把责任和终审留给人，需要把负责人和执行方分开说清。 |
| **分身可以直接做什么** | “答疑”是转述获准内容，还是自己生成业务结论？后者与 M-OPT 的分工不符，不能只用“轻型”来解释。 |
| **一个人有多个业务域时怎么办** | POC 可以先配一个分身，但不能把“永远只有一个分身”写成长期定义。 |

“我的团队”先明确为**本人使用助理、分身和专家的个人入口**，不是新的 Agent 类型，也不是必须新建的 IM 群。完整的团队界面和成长陪伴可以后做；POC 先复用现有入口。

这里要定的是角色能做什么、能用哪些信息，不是现在就列齐每个岗位装什么技能。默认能力清单交给配置和 onboarding 工作。

**本轮产出：一页角色分工与权限说明，把未确认的边界单独拿出来讨论。** 对应 H1、B1、B3、B5，以及 C2 中“默认数量与长期定义”的区别。

## 三、🔴 长期团队、项目和任务怎么组织

**要解决的是长期协作，不只是少拉几个群。** 一批人会持续共事，他们的共同资料、工作上下文和共享记忆，需要有稳定的归属，不能随每次会议或一批任务重新开始。

“班委会周报 OKR”只是用户举的例子。产品不能内置“本周 OKR”这一套业务结构，分类方式、名称和工作周期都应由用户决定。

上一版“常驻群关联每次新建的项目”撤回。它只解决群的复用，没有解决共享上下文和共享记忆如何持续积累，不能作为这个问题的完整解法。

### 3.1 现在保留三种选择

| 方案 | 长期的人、资料和记忆放哪里 | 需要说清的区别 |
| --- | --- | --- |
| **1. 保留两层，用自定义分类组织任务** | 现有“项目”作为长期协作容器，任务用用户自定义的标签或分组整理。 | 分类只负责整理和筛选，不自动成为独立的权限或记忆边界。 |
| **2. 项目—子项目—任务** | 父项目承载长期合作，子项目组织不同工作。 | 子项目是单纯分组，还是有自己的目标、进度和结项？不能只换一个名字。 |
| **3. 恢复空间—项目—任务** | 空间承载长期成员、共享资料和记忆，项目组织具体工作，任务负责执行。 | 需要重新讲清空间与项目的区别，而不是为了少一个词丢掉长期协作这一层。 |

方案 2 和方案 3 都保留了长期承载层，但要确认：最上层究竟代表一个大项目，还是一组长期合作的人。名字应该帮助用户理解这个区别。

项目或子项目由用户按工作需要建立，**不默认一次会议、一周工作就新建一个项目**。当前不预选方案，先把下面四件事定清：

- 长期成员、共享上下文和共享记忆归到哪里？
- 不同工作怎样分开，任务属于哪一项工作？
- 上下层哪些资料可以共用，哪些需要隔离？
- 某项工作结束后，历史成果和可复用记忆怎样留下？

标签方案也不能要求用户每次记得说“挂什么标签”。页面或 CLI 已有明确归属时可以带上；不明确就问一句，并在创建时让用户看见任务会放到哪里。分类名称仍由用户定义。

**本轮产出：选定层级方案，说明成员、任务、资料和记忆的归属。** 这是 D2 / D3 背后现在必须解决的问题；具体筛选项和列表样式可以随后细化。

## 四、🔴 个人记忆、共享记忆和分身怎么衔接

**现在就要设计记忆存到哪里、谁能用、怎么传，不等于 POC 要做完整的记忆平台。**

先把四种内容分开：

| 内容 | 放什么 | 谁决定怎么用 |
| --- | --- | --- |
| **个人记忆** | 我的偏好、习惯和个人工作经验。 | 本人决定；涉及组织资料时，仍受原资料权限约束。 |
| **共享上下文（Shared Context）** | 当前工作的目标、材料、讨论和进度。 | 按所在工作范围授权，不把全部过程自动存成长期记忆。 |
| **共享记忆（Shared Memory）** | 团队确认的事实、规则和可复用经验。 | 留在长期协作范围内，由有权限的维护者确认和更新。 |
| **分身的记忆切片** | 这个业务域内允许分身使用的一小部分信息。 | 本人审核个人信息的分享，组织信息还须符合组织授权。 |

共享记忆的长期归属，要和第三章的层级方案一起定。**能读一份共享资料，不等于可以把全文永久复制进个人记忆，更不等于可以继续转给其他业务域。**

### 4.1 现在要设计的，是这四个动作

1. **沉淀**：助理整理出值得记的内容，区分个人经验和团队结论，由本人或有权限的共享记忆维护者确认后保存。
2. **分发**：从获准使用的记忆和当前材料中选出切片，明确给哪个分身、用于哪个业务域、何时失效。
3. **回流**：分身把外面的请求、进度和反馈带回来，需要长期保留的内容再确认存到个人还是共享记忆。
4. **更新与停用**：来源变了、权限撤回了，旧切片要更新或停止使用；本机离线时，分身只能使用此前获准且仍有效的内容。

个人经验要变成团队经验，也走“选出内容—检查可分享范围—有权限的人确认”这条路，不做个人记忆与共享记忆的全量互拷。

### 4.2 POC 先做到哪一步

先采用**人工选材料、预览、确认分享**的小流程，并保留查看已分享内容、更新和停用的办法。技术上怎样传，可以由客户端、服务端和记忆研发一起确定。

全自动提炼经验、完整知识管理后台、全量跨域同步和复杂运营规则，不作为本期前提。分身收到新消息，也不能自动把它写成我的长期偏好。

**本轮产出：一张记忆归属与流转说明，外加一条人工审核分享的小流程。** 这承接 H1、B3，以及会议记忆专题；“别重复干活”不再单独扩大成一个新系统。

## 五、🔴 给领导选择的角色命名方案

**这个是明确要交的材料，保留为独立事项。**

新版逐字稿中，昊总在 10:34:49—10:36:35 要求准备几组名称，降低理解成本，让领导参与选择；陈博在 10:36:44—10:37:14 复述并确认：先讲清三类角色做什么，再让领导定名字。[T2]

交付内容保持简单：

1. 两到三组角色名称，对应同一套职责。
2. 每个角色一句话解释。
3. 一个共同的使用例子，说明三者怎样配合。
4. 一组推荐及理由。

**让领导选的是名字，不是几套互相冲突的角色定义。** EVA 产品品牌与个人助理名字也要分开，允许用户给自己的助理改名。[A1；T2，09:38:14—09:38:37]

这对应 A1 和 H8 的命名部分。H8 的“全新 AI 原生交互”另作后续体验工作，不与命名捆成一项大交付。

## 六、其余需求怎么取舍

**不再逐条展开成新功能。** 红灯只保留第二至第五章的四项设计或材料交付；已经能对应的概念结项，其余明确去向。

### 6.1 🟢 当前概念已对齐，不再追加工作

| 原需求 | 本轮判断 |
| --- | --- |
| **H5：OPT / M-OPT** | 🟢 **Done（概念对齐）**。一个人带 AI 团队，多个人再协作，现有概念可以对应。 |
| **H7：先有原则再做功能** | 🟢 已有 M-OPT 作为设计依据，不另外承诺一套理论和标准体系建设。 |
| **B4：助理私有、专家不入群** | 🟢 方向已定，不再把“专家必须进群”当作缺口。 |
| **C4 / D4：工作方式与任务来源** | 🟢 个人与多人协作、任务来源和人确认已有概念，沿用即可，不代表全部交互已完成。 |

“分身独立于本机”“本机可有多个内部助理”“本人私有调用助理”也沿用第一章，不重复打开概念争议。

### 6.2 🟡 移出本轮必须设计的清单，保留明确去向

黄灯不是同一种原因，下面分别标明；它们不是都归运营，也不是全部取消。

| 原需求 | 类型与去向 |
| --- | --- |
| **H2 / H3 / C2 / C5：默认技能、岗位配置、个性化** | **配置与 onboarding**：角色允许做什么在第二章定；具体装什么、怎么推荐，由能力维护和运营安排。 |
| **B2：别重复干活** | **使用约定与执行策略**：先复用已有成果，不单开跨 Agent 自动防重复系统；必要的信息互通并入第四章。 |
| **C1 / C3 / E5 / H8 交互部分：我的团队、主动提醒、成长陪伴** | **后续产品体验**：保留个人入口的定位；完整界面、主动服务和陪伴机制按试点需要排，不要求现在全部设计完。 |
| **H4：完整生命周期走一遍** | **设计验证**：用小场景检查四项设计，不把每个生命周期场景都变成待开发功能。 |
| **D1 / D5：项目计划、文件分类等细节** | **常规产品细化**：成员、任务和资料归属在第三章定；详细表单、分类和布局随后安排。 |
| **E1 / E2：已有系统和数字员工接入** | **外部依赖与接入研发**：客户提供可用接口和能力，按现有连接方式验证，不默认由融合产品团队重建。 |
| **H6 / E3：运营评价、老板四问** | **业务运营与价值评价**：不列为本期产品新模块；选定的 POC 仍要验证能否交付正确结果。 |
| **E4：发版、分工、重复建设、例会** | **项目管理与研发协作**：放到执行计划，不作为产品概念问题；其中记忆设计已归第四章。 |

### 6.3 接入这件事，只保留常规边界

已有系统或数字员工，提供了获准调用的接口，例如 MCP 或 CLI，就沿用“连接 / 专家能力”的方式接入，由接入研发验证权限、输入输出和结果是否可用。

没有可用接口，又不允许开放，就先不纳入自动接入范围；可以换试点或先由人操作。**不把“客户暂时没有接口”转成“POC 产品团队要重做那个系统”。** 有接口也不等于已经接通或验收通过。

客户能力负责人负责提供和维护现有能力；产品团队只确定本次用什么验证场景，接入研发确认能否调用。是否纳入 POC，由项目负责人结合依赖和交付范围决定，不因会上提到就自动承诺。
